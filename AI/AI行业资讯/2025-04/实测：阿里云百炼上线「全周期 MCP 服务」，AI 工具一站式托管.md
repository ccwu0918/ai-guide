長話短說：

今天，**阿里雲百鍊正式上線了 MCP（Model Context Protocol）服務的完整平臺能力**，覆蓋從服務註冊、雲託管，到 Agent 呼叫、流程組合的全生命週期。

## 01 ｜ MCP 能幹啥

這裡我測了兩個典型的 Agent 例子，分別是「導航推薦助手」和「網頁抓取助手」。

![](https://imagedelivery.net/qGOFcc1O8XwTZW3W1JAHHg/cb4f10bd-5370-445a-9262-9cb40a1a5300/public)

在百鍊上，可以透過多種方式，構建 Agent

### 單 MCP 呼叫：高德地圖 + AI 導遊

這是一個簡單的智慧體應用，目標是：**根據使用者的旅行目的地，生成當天的城市遊推薦方案，並串聯天氣、位置、美食和導航任務。**

整個過程沒有寫程式碼，只是在百鍊廣場上開通高德地圖（Amap Maps）的 MCP 服務，然後在「建立智慧體應用」後，拉取這個 MCP 服務。

下面的影片是原速，可以感受下：

輸入一個城市，比如“西安”，Agent 會自動：

1.  1\. 查詢當天西安天氣
2.  2\. 基於定位列出附近的景點、餐飲店
3.  3\. 安排出行路徑（如騎行/地鐵）
4.  4\. 給出推薦行程描述和地圖跳轉連結

整個任務鏈由 Agent 自動執行，所有服務來自百鍊託管的 MCP 介面，無需我們部署伺服器、寫 API 程式碼或解析引數文件。

---

### 多 MCP 呼叫：網頁抓取 + 資料生成

這是一個稍微複雜的 Case，透過構建工作流，讓 AI 幫我取抓取網頁，然後進行頁面提取，最後儲存在 Notion 裡。

從流程上來說，就是

1.  1\. 大模型識別對話中的 URL
2.  2\. 透過 Firecrawl 抓取這個頁面的資訊
3.  3\. 透過大模型對資訊進行總結
4.  4\. 將總結後的資訊，上傳到 Notion

這一套工具鏈同樣透過 MCP 服務構建，串聯了「Firecrawl」、大模型本身的處理，以及「Notion」等多個內容，全部可複用、可組合，也不依賴特定模型。

## 02 ｜百鍊上的 MCP 怎麼用？

在百鍊 MCP 平臺上，開發者可以透過兩種方式使用 MCP 服務。

地址在這裡：https://bailian.console.aliyun.com/?tab=app#/mcp-manage

### 第一種：直接用官方託管服務（選服務）

目前，百鍊已經上線了 15 款 MCP 的雲服務，並提供了 61 款社群 MCP 的介紹，更多的還在路上。

![](https://imagedelivery.net/qGOFcc1O8XwTZW3W1JAHHg/78367a90-f9d4-4f46-bd97-3f31a9466500/public)

以上服務已部署，更多服務在路上

![](https://imagedelivery.net/qGOFcc1O8XwTZW3W1JAHHg/772819d4-d08e-472b-46c1-17fb62a6bd00/public)

這些都是社群 MCP

這種方式適合絕大多數場景，幾乎“零門檻”：

1.  1\. 開啟 MCP 服務廣場
2.  2\. 找到你需要的服務（如高德、GitHub、Notion）
3.  3\. 點開通，填寫 API key（如有）
4.  4\. 就能在 Agent 或流程中直接呼叫

服務由百鍊託管在函式計算上，呼叫即載入、透過 API 按量計費。

上面測試的高德導航、網頁抓取等場景，都是走這一套流程。開發者不需要管部署，不需要寫 Glue Code，呼叫非常穩定，尤其適合原型驗證和組合式 Agent 設計。

> 據知情人士透露
>
> 百鍊 MCP 服務將是阿里 AI 商業化重要落棋。
>
> 未來，阿里的服務，以及更多的三方應用，都將逐步上線到百鍊，來滿足任意場景 Agent 的開發需求。

---

### 第二種：自建服務（註冊服務）

如果你有自己的 API，或者需要引入社群裡的 MCP server（比如從 GitHub 上 clone 的開源專案），也可以走“自建部署”的路徑：

1.  1\. 開啟“註冊服務”介面
2.  2\. 貼一下  `npx`  安裝 或 Python 指令碼（Python  暫還是灰的）
3.  3\. 系統會自動建立一個函式計算例項來託管你的服務
4.  4\. 註冊成功後，該服務就能作為 MCP 工具被呼叫

![](https://imagedelivery.net/qGOFcc1O8XwTZW3W1JAHHg/3eeb83ca-877b-423e-15b1-57b813eb1e00/public)

bailian.console.aliyun.com/?tab=app#/mcp-manage/create

這條路徑稍微偏“開發者向”，但整個過程比傳統的伺服器部署方式要簡單得多：

- • 不需要自己買機器
- • 不需要配置負載均衡或許可權系統
- • 可以透過文字配置定義 schema，自動生成模型呼叫示例

比較適合企業開發者將內部服務 MCP 化，或技術團隊接入外部服務做統一封裝。一句話總結就是：

> 以前做一個“外掛”要寫程式碼、跑服務、調結構，現在開個服務就是點幾下配置。

## 03 ｜ MCP 和 Plugin 的區別

我相信，很多人還會有個反應：**這不就是 Plugin？**

對此，我也特意和百鍊的朋友聊了這個問題，得到的回答很明確：

> Plugin 是為某個模型寫的私有介面描述；MCP 是跨模型、跨平臺可複用的通用協議。

差別主要體現在三個層面：

### 協議開放性

Plugin 是各廠商其自己模型設計的，無法直接複用到其他模型平臺。而 MCP 的目標是**讓所有模型理解同一種“服務語言”**。無論 Claude、GPT、百鍊自有模型，理論上都能讀懂相同的 MCP 介面描述，並做出合理排程。

![](https://imagedelivery.net/qGOFcc1O8XwTZW3W1JAHHg/8d143006-f87e-4c7a-fb2b-6d170f3a2300/public)

MCP 和 Plugin 的區別 be like

### 服務部署方式

Plugin 開發者需要自己部署服務，並管理呼叫、安全、負載等細節。MCP 在百鍊的實現中，**服務由平臺託管**，開發者只需提供邏輯，其他都交由平臺自動完成（如函式計算、鑑權轉發等）。

### 呼叫正規化

Plugin 更像是“硬編碼呼叫”：定義好 schema，模型識別後呼叫一次函式。MCP 支援的是**多步排程、多工具組合**，更適合 Agent 執行復雜任務時使用。

---

> 在我看來
>
> MCP 是對 Plugin/Function Calling/Tool Using 再封裝了一輪，這樣遷移環境的時候，節省了一部分調配的功夫。

---

## 寫在最後：從工程對接，到能力平臺

**在 MCP 之前，讓 AI 呼叫外部工具，更像是一項繁瑣的工程任務**，你需要寫描述、調介面、配引數、部署服務等等...**現在，這些正在被重新定義為一種標準化的、平臺化的能力**。

在我看來，這是一種焦點的轉移：

- • **過去，重心在“人”**：工具主要服務於開發者，AI 需要被動適應。
- • **現在，重心在“AI”**：服務被設計成易於 AI 理解和使用，主動擁抱模型。

非常有趣。
